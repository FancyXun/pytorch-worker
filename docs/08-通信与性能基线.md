# PyTorch 分布式训练（八）：通信与性能基线（魔改前必做）

**源码与 API 版本**：本文以官方 **PyTorch 2.5.x** 为准，源码参考 **[v2.5.0](https://github.com/pytorch/pytorch/releases/tag/v2.5.0)**。

在讲“怎么魔改 DDP”之前，建议先把原生基线测准。否则很容易出现：改了很多代码，最后发现瓶颈根本不在你改的那一段。

## 1. 先定义你要看的 6 个指标

1. **Step time**（每步耗时，P50/P90）。  
2. **Samples/sec**（吞吐）。  
3. **通信时间占比**（NCCL/collective 占 step 的比例）。  
4. **计算-通信重叠程度**（时间轴交叠）。  
5. **各 rank 抖动**（最慢 rank 与中位 rank 差值）。  
6. **收敛一致性**（loss 曲线是否对齐、是否出现 rank 漂移）。

只要这 6 个指标稳定，后面魔改的收益和回归才可量化。

## 2. 最小化实验矩阵（建议先做）

- 单机 1 卡（基线）。  
- 单机 N 卡 DDP。  
- 多机 N 卡 DDP（如有条件）。

保持一致：模型、batch、数据、优化器、随机种子。只改并行配置。

## 3. 工具链：至少保留两条

- **PyTorch Profiler**：看 operator 级别时间分布。  
- **Nsight Systems**（GPU/NCCL 场景）：看 CUDA kernel 与 NCCL kernel 的重叠关系。

若你只看总吞吐，很难判断“变快是算子变快了，还是通信掩蔽得更好了”。

## 4. 通信相关环境变量（排障常用）

常见排障会用到如下环境变量（具体行为以官方文档与 NCCL 版本为准）：

- `NCCL_DEBUG=INFO`（通信日志）  
- `TORCH_DISTRIBUTED_DEBUG=DETAIL`（分布式调试信息）  
- `TORCH_NCCL_BLOCKING_WAIT=1`（超时与错误行为更可观测）

说明入口：
- PyTorch 分布式文档  
  <https://pytorch.org/docs/2.5/distributed.html>
- NCCL 用户指南  
  <https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/index.html>

## 5. 判断瓶颈在“通信”还是“计算”的实用规则

- 若单卡已满载、N 卡线性扩展差，同时 NCCL 占比很高：优先看通信侧。  
- 若 NCCL 占比不高但吞吐仍差：优先看数据输入、算子效率、内核选择。  
- 若某一 rank 明显慢：先查数据分布、CPU 绑核、网卡或 PCIe 拓扑偏差。

## 6. 与 DDP 参数的联动关系

性能实验时，至少记录以下 DDP 相关参数，避免“结果不可复现”：

- `bucket_cap_mb`  
- `find_unused_parameters`  
- `gradient_as_bucket_view`  
- 是否使用 `no_sync()` 进行梯度累积  
- 是否注册 comm hook

这些参数会直接改变通信时序与内存行为，不记录就无法解释曲线变化。

## 7. 给后续魔改预留的对照模板

在你后续文章里，可以固定使用下面的对照模板：

- **改动前（原生 2.5 DDP）**：6 个指标数值 + profiler 截图。  
- **改动后（魔改分支）**：同样 6 个指标 + 同样工具链。  
- **收益归因**：明确是“通信减少”“重叠提升”还是“CPU 开销下降”。

这样读者能快速判断改动价值，也更容易复现实验。
