# PyTorch 分布式训练（四）：实践中的检查项与排错思路

**源码与 API 版本**：文中摘录的代码与 API 行为均以官方 **PyTorch 2.5.x** 为准；代码定位使用 GitHub 标签 **[v2.5.0](https://github.com/pytorch/pytorch/releases/tag/v2.5.0)**，与 [PyTorch 2.5 文档](https://pytorch.org/docs/2.5/) 一致。

本篇列出使用 `torch.distributed` 与 `DistributedDataParallel` 时**常见的约束、现象与排错顺序**，均针对对称数据并行的典型用法。


## 1. 进程与设备绑定

- **一进程一卡**是 GPU 上最常见、也最不容易踩坑的模式：`local_rank` 决定本进程用哪张 GPU，`CUDA_VISIBLE_DEVICES` 与启动器传入的 rank 组合要一致。  
- 若出现「两个进程绑到同一张 GPU」，通常会表现为显存异常、随机卡顿或错误；启动脚本与集群调度里要显式检查。


## 2. 模型与参数顺序在各 rank 必须一致

`DistributedDataParallel` 的文档强调：各分布式进程上的模型**结构相同**，且**参数注册顺序一致**；梯度 `allreduce` 的顺序与参数注册顺序相关。

出处：[torch/nn/parallel/distributed.py（v2.5.0，约 L465–L471）](https://github.com/pytorch/pytorch/blob/v2.5.0/torch/nn/parallel/distributed.py#L465-L471)

```text
    .. warning::
        This module assumes all parameters are registered in the model of each
        distributed processes are in the same order. The module itself will
        conduct gradient ``allreduce`` following the reverse order of the
        registered parameters of the model. In other words, it is users'
        responsibility to ensure that each distributed process has the exact
        same model and thus the exact same parameter registration order.
```

若某些 rank 上多注册或少注册了参数（例如条件导入导致模块不一致），错误往往**不会**以清晰的 Python 异常形式出现在第一行，而是表现为 loss 异常、NaN、或各卡数值漂移。多机训练前应用**同一份代码与同一份配置**在各 rank 启动，并在首轮打印一次参数名与 shape 做抽样对比。


## 3. 数据是否真做到了「各 rank 一份子集」

DDP 不替你切 batch。若所有 rank 读同一顺序、同一子集的数据，则相当于同一批样本被重复算多遍，梯度再平均，**与「扩大全局 batch」不是一回事**。应使用 **`DistributedSampler`**（或等价逻辑），并注意 **`set_epoch`** 以便每个 epoch 洗牌不同。梯度累积时，要清楚「有效全局 batch」如何随累积步数变化。


## 4. 损失缩放与「等效 batch」

多节点、每节点 batch 为 \(N\) 时，若损失在样本维用 **sum** 而不是 **mean**，再叠加跨 rank 的梯度平均，与「单机一次 batch = 总样本数」之间的比例会差一个与进程数相关的因子。`DistributedDataParallel` 文档中有专门说明（见第一篇中同一 **note** 的引用与 [官方文档](https://pytorch.org/docs/2.5/generated/torch.nn.parallel.DistributedDataParallel.html)）。调学习率、权重衰减、warmup 时，应自洽地指定：**你写的 `loss` 定义**、**batch 总大小**、**梯度累积步数**三者一致。


## 5. BatchNorm、SyncBatchNorm 与 `eval()`

BatchNorm 的 running 统计在 DDP 文档中说明由 **rank 0 广播** buffer。若任务需要「全局 batch 上统计一致」而不是「各 rank 本地 batch 统计」，要使用 **`SyncBatchNorm`** 或等价替换，并理解其对通信与性能的影响。推理阶段 **`model.eval()`** 会关闭部分随机性并使用 running 统计；多卡推理若只跑在 rank 0，要避免其它 rank 仍执行会写 buffer 的路径。


## 6. `find_unused_parameters` 与静态图

存在「某些迭代里部分参数不参与 loss」的动态图时，可能需要 **`find_unused_parameters=True`** 以保证正确性，代价是额外开销。若模型结构固定、每次前向都用到全部参数，应保持 **`False`**。与 `torch.utils.checkpoint` 的组合行为以当前版本文档为准。


## 7. 通信超时与 NCCL 环境变量

多机训练常见问题是某 rank 掉队导致 collective 永远等。PyTorch 与 NCCL 提供超时、异步错误检测、调试环境变量等机制（名称与默认值随版本变化）。遇到 hang 时，应缩小复现规模（两机两卡）、打开分布式调试日志、检查网络与防火墙是否放行训练端口，而不是先盲目调大 batch。


## 8. 性能分析：先分清瓶颈在算子还是在通信

- 使用 **PyTorch Profiler**、**Nsight Systems** 等工具，看时间轴上 **NCCL** 或后端 collective 与 **CUDA kernel** 的占比。  
- 若通信占比高：考虑 batch、模型宽度、梯度累积、通信压缩、拓扑与 NIC 配置；分桶与 overlap 已由 `Reducer` 与后端承担大部分，仍可通过 **`bucket_cap_mb`** 等（以文档为准）做有限调节。  
- 若计算占比高：分布式本身不是主矛盾，应回到算子、混合精度、IO 等方向。
